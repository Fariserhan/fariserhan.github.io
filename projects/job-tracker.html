A job application tracker with its own data warehouse

The synthetic demo tracks 168 applications without losing earlier milestones when a status changes.

Synthetic data throughout. Every application count, rate and chart on this page comes from the public sample report generated 16 October 2026. These are demonstration results, not my personal job search.

Application emails arrive separately. A current-status spreadsheet can lose an interview milestone when a rejection follows.

The tracker reads Gmail and keeps dated application events locally. Shared SQL definitions feed the app, reports and exports.

The question I needed to answer

I wanted consistent answers to two questions: where do applications stop, and how long do replies take?

I built the email ingestion, rule-based parsing, event storage, reporting database and outputs with AI assistance.

From inbox to evidence

Architecture / Scroll to follow a record

The graphic follows one record through five stages. Each stage is also a button: focus, tap or click to inspect and pin it.

01 / SOURCE

Read the inbox without changing it.

The tracker reads Gmail without changing it. It searches job-board and recruitment-system emails, then excludes known marketing messages.

It reads basic email details first and fetches the body only when needed. Each update rechecks an overlapping period to recover missed messages.

02 / PARSE

Rules make the first decision.

Rules identify application events, their status, employer and role.

An optional AI check handles unclear messages. It is off by default, saves repeat results and has a monthly spending limit; it does not replace testing the email rules.

03 / PRESERVE

Unknown is not zero.

Each event uses the source email’s date. Missing reply dates stay blank and are excluded from reply-time calculations.

SQLite stores applications and events locally. Email bodies stay in a separate local store and are excluded from reports and exports.

04 / MODEL

Build a reliable reporting database

Sixteen SQL models organise the reporting database in DuckDB, a fast local analytics database. They are built and tested with dbt, a tool that runs SQL models in order and checks their output. A central table of applications and status events links to employer, date and platform tables.

Each update is prepared separately, then replaces the old reporting database only when ready. An interrupted update leaves the old version usable; checks reject negative durations and preserve missing dates.

05 / COMMUNICATE

Use the same numbers in every output

One set of SQL definitions feeds the app, report and Excel/CSV export pack. The pack also includes calculations for Power BI and Tableau.

Charts keep the furthest stage reached and show uncertainty intervals for rates. Small samples get warnings rather than confident rankings.

A funnel that remembers the interview

The funnel uses the furthest stage reached. A later rejection does not erase an earlier interview.

A high rate can hide a very small sample

One referral received a reply in the synthetic sample: 100% from just one application. The uncertainty interval shows why that is weak evidence. (“Direct ATS” means applying straight through an employer’s own recruitment system, or applicant tracking system.)

The latest month has had less time

Recent applications have had less time to receive replies, so their response rates are still provisional. For reply times, the tracker uses the Kaplan–Meier method, a standard way to estimate waiting times that counts applications still awaiting a reply instead of dropping them.

What this misses

  • The 168 synthetic applications demonstrate the pipeline, not job-market performance or a real inbox.
  • The email rules were checked on a small set of hand-labelled emails they had never seen, so their accuracy is still uncertain. Scores on the emails used to write the rules are not an independent check.
  • Inbox-only tracking misses applications without a matching email.
  • A channel comparison does not control for role, applicant or employer differences.

What I’d do next

Hand-label more unseen test emails, investigate ambiguous status wording and inspect disagreements rather than tuning to a headline score.
