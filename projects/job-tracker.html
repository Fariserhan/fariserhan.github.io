02 / Case study / Job application tracker

The biggest drop happens before the first reply.

In the synthetic demo, 42 of 168 applications receive a response. Behind that finding is a tracker built to preserve event history, keep unknowns honest and report from one set of SQL definitions.

Synthetic data throughout. Every application count, rate and chart on this page comes from the public sample report generated 16 October 2026. These are demonstration results, not my personal job search.

An inbox is a poor database. Confirmations, assessments, invitations and rejections arrive as separate messages, mixed with job alerts and unrelated mail. A current-status spreadsheet loses the journey: an interview can disappear the moment a rejection arrives.

I built a local-first tracker that reads Gmail, identifies application events and keeps a dated history. It turns that history into a small warehouse, then uses shared SQL definitions for the app, report and export pack.

The question I needed to answer

Where do applications stop, how long do replies take, and can I trust the denominator? The first task was to make those questions mean the same thing in every output.

My contribution covers ingestion, deterministic parsing, event storage, warehouse modelling and reporting. AI assistance supported the build; the definitions and verification rules are explicit in the project.

From inbox to evidence

Architecture / Scroll to follow a record

The graphic follows one record through five stages. Each stage is also a button: focus, tap or click to inspect and pin it.

01 / SOURCE

Read the inbox without changing it.

Gmail access is read-only. Searches combine known job-board and ATS senders with subject and body wording, then subtract known marketing templates.

Metadata comes first. Bodies are fetched only when the first verdict needs more information. Incremental sync includes an overlap so a previously missed message can be recovered.

02 / PARSE

Rules make the first decision.

Separate rules decide whether a message is an application event, which status it represents, and whether the employer and role are usable.

The optional AI second opinion handles ambiguous messages only. It is off by default, cached per message and bounded by a monthly budget. It is not a substitute for parser evaluation.

03 / PRESERVE

Unknown is not zero.

The event log uses the date on the source email, rather than the time the tracker happened to sync it. A missing reply date stays NULL and is excluded from timing metrics.

Application and event records live in SQLite. Email bodies stay in the local cache; they do not enter the warehouse or the export pack.

04 / MODEL

Build a warehouse you can rebuild.

The same dbt SQL files define staging, milestones and a DuckDB star schema. Application facts and status-event facts link to dimensions such as employer, date and platform.

A build writes to a staging file before an atomic swap. If a build is interrupted, the previous warehouse remains available. Data checks include non-negative durations and unknown dates staying NULL.

05 / COMMUNICATE

One definition, several outputs.

One SQL metric layer feeds the Streamlit app, a findings report and the BI export pack: Excel, star-schema CSVs, DAX measures and Tableau calculations.

The funnel counts the furthest stage ever reached. Rates carry Wilson intervals. Small channel samples get explicit warnings instead of confident rankings.

A funnel that remembers the interview

An application rejected after an interview still reached interview. Counting only its current status would erase that milestone and distort the funnel. This version uses the furthest stage in its event history.

“Unknown reply dates are excluded from timing metrics, never treated as zero.”

Measurement rule · Project sample report

A high rate can hide a very small sample

A referral has a 100% response rate in this synthetic report, from one application. The interval makes the weakness visible. Channel differences describe this generated sample; they do not establish a causal advantage or predict a real search.

The latest month has had less time

Monthly response rates are not equally mature. A recent application can still get a reply. Pending applications therefore matter both to cohort comparisons and to the Kaplan–Meier reply-time calculation.

What this misses

  • Synthetic data demonstrates the pipeline, not job-market performance.
  • A parser evaluated on a small blind holdout still has uncertainty; development-set performance is not independent validation.
  • Inbox-only tracking misses applications without a matching email.
  • A channel comparison does not control for role, applicant or employer differences.

What I’d do next

Expand the independently labelled holdout, investigate ambiguous status wording and inspect disagreements rather than tuning to a headline score.

Keep the collected test count dated, and update the CV when its testing claim is revised.

Keep the same definitions across all exports, and make missing-date coverage part of every timing report.

What the project proves

The useful result is a traceable data product: an event has a source, a metric has a definition, and a chart carries its limitation. The demo lets another reader inspect that chain without exposing a real inbox.
