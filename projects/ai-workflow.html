My role
Choose the tool, scope the task, inspect and verify the output

The run table records task outcomes, not accuracy or productivity. No prompts, accounts or personal usage details are published.

I use AI to draft, search, code and summarise. I give it a bounded task and check the output against source evidence.

I set the brief, choose tools and resolve conflicting results. I check claims, figures, calculations and working outputs before delivery.

I log the model, effort, duration and outcome. Failed or slow tasks help me adjust the next request.

THE LEARNING LOOP

Use the log to change the next decision.

After a timeout or usage limit, I shrink the task or change tools.

The log changes the way I scope work

Of 436 logged runs, 323 finished successfully, 61 hit the five-hour limit, 31 timed out and 21 failed otherwise. These are process outcomes, not accuracy scores.

I split long requests into smaller tasks or change tools when a run fails.

Three tools support different parts of the work

The PowerShell tray app shows capacity across three service rows. It refreshes in the background and keeps the last good reading during temporary limits.

A Node script compares model listings from models.dev, OpenRouter and LiteLLM. Its dated snapshot scanned 8,114, 455 and 4,182 entries respectively; this is not a live price feed.

These tools help me choose capacity and compare costs. I remain responsible for checking the finished work.

What this misses

  • A successful run is not a correct answer. The log does not grade content quality.
  • Run counts cover Codex only; they are not every AI request or every kind of task.
  • Prices and model listings move. The market figure is a 23 September 2026 snapshot.
  • Quota rows depend on external service readings; the page does not query an account.

What I’d do next

Tag runs by task type and record whether the delivered output passed its acceptance checks. That would distinguish a clean process exit from useful work.
